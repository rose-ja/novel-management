# 单次功能变更执行手册

每个功能、修复或技术改造建立一个独立目录：`changes/CHG-001-short-name/`。

## F1：拆解

1. 确认变更目标和用户价值。
2. 阅读相关 Spec、架构、ADR、AGENTS.md。
3. 检查当前代码实际结构，不根据旧文档猜测。
4. 定义范围、非目标、文件范围和接口影响。
5. 设计垂直切片与执行顺序。
6. 定义测试数据、异常路径、DoD、回滚。
7. 输出 proposal/design/tasks/checklist。
8. 对需求或架构冲突暂停并请求确认。

通过：每项任务可执行，范围可控，验收可判定。

## F2：实现

1. 检查 Git 分支、工作区和未提交修改。
2. 读取 AGENTS.md 与变更任务卡。
3. 按任务顺序实施；每个任务后汇报文件和结果。
4. 不得顺手重构无关代码。
5. 超范围变更必须暂停。
6. 完成后输出 Diff 摘要和已知问题。

## F3：自测

按项目实际命令执行：
- lint
- format check
- typecheck
- unit tests
- integration tests（涉及跨模块/数据库/API 时）
- build

记录真实命令、退出状态、失败原因和修复情况。没有对应命令时写 `N/A` 并说明原因。

## F4：独立审查

Reviewer 读取实际 Diff、Spec、任务卡和测试报告。按正确性、需求一致性、副作用、安全、性能、可维护性、测试充分性审查。

问题等级：
- P0：阻断交付，必须修复。
- P1：重要问题，必须修复或经人批准豁免。
- P2：建议，记录为技术债或后续任务。

## F5：修复复审

逐条修复 P0/P1。修复后重跑受影响测试，并由独立 Reviewer 复核。禁止带未处理 P0 进入最终验收。

## F6：集成与 E2E

至少覆盖：
- 核心成功路径
- 关键异常路径
- 权限/数据隔离（适用时）
- 边界条件
- 受影响旧功能回归

实际执行并保存日志、截图、报告。测试失败必须定位，不得用“理论上没问题”代替执行。

## F7：人工验收

人检查：
- 业务行为是否正确
- UI/UX 是否符合设计（适用时）
- 测试证据是否可信
- 变更是否越界
- 安全、数据和兼容性风险
- 回滚是否可行

结论：ACCEPT / REWORK / REPLAN。

## F8：PR/MR

描述必须包含：
- 变更目标
- 对应 Spec
- 文件/模块变更
- 测试命令和结果
- E2E 证据
- 风险和回滚
- 人工评审关注点

## F9：合并与发布

1. 合并前确认 CI 通过。
2. 按发布策略部署。
3. 运行部署后 Smoke Test。
4. 检查日志、错误率和关键业务行为。
5. 失败时按预案回滚或修复。
6. 生产操作必须获得人工授权。

## F10：Spec 同步与归档

1. 把已实现行为合并进 `project/specs/`。
2. 更新受影响的架构、API、数据模型和 ADR。
3. 更新路线图和变更状态。
4. 保存 verification。
5. 将变更目录移入 `changes/archive/`。
6. 检查下一个变更的依赖是否满足。
