## 2. 项目概述

### 2.1 背景

写小说时，人物、人物图片、境界、称号、所属势力、地点、势力成员、排行榜等信息分散在飞书文档中，依靠标题层级、括号备注和列表混合表达。随着设定增多，会出现三个问题：

1. 查找成本高：想确认一个角色的势力、境界或榜单名次，需要在多个章节和列表之间翻找。
2. 同一实体多名称：一个人物可能同时拥有本名、化名、称号和境界描述，例如「司空摘天（神逆）（山海帝君）（帝境五重天）」，没有统一的主名称与检索入口。
3. 修改容易不一致：改名、换势力、调整境界后，需要人工同步多处，容易产生矛盾设定。

### 2.2 核心问题

本项目要解决的不是「如何写小说」，而是：

- 如何把散落的设定变成**可检索、可关联、可维护**的结构化资料。
- 如何保证同一实体只有一份权威数据，修改后所有关联位置自动同步。
- 如何让多本小说各自拥有独立世界观，又不互相污染。

### 2.3 产品定位

**小说设定的结构化资料库 + 检索与一致性维护工具。**

它不是：

- 小说正文写作工具；
- 关系图谱或可视化大屏工具；
- 多人协作平台；
- AI 内容生成工具。

### 2.4 输入事实（来自飞书《正文》）

- 文档性质：世界观设定集，不是小说正文。
- 已包含六类内容：纪元史、星空地理、星曜 / 星命 / 十五境体系、三张榜单、万族传（种族 / 势力 / 分支 / 首领）、人物与配图。
- 三张榜单：封神榜、草黄纸、星火榜，飞书现状为 1-100 的固定席位，目前基本为空；产品支持 1–200 席自定义，默认 100。
- 人物是多值实体：可同时拥有本名、化名、称号、境界（含重天等子层级），并归属某个势力或分支。
- 势力存在层级：万族 → 族 → 分支（如山海妖族 → 山海七神天 → 心神天 / 水神天 / …），分支下有首领与成员。
- 文档中已有真实人物配图，说明「人物图片」是实际需求，不是设想。
- 当前信息依靠「标题层级 + 括号备注 + 列表」混合表达，没有统一字段，这正是检索困难与不一致的根源。

## 3. 项目目标

### 3.1 长期目标

- 成为作者本人管理小说设定的**唯一可信数据源**，替代飞书文档的日常查阅。
- 支持多本小说，每本拥有独立世界观、独立体系与独立数据。
- 为后续写作、设定扩展和系列作品复用提供可靠基础。

### 3.2 第一版目标

- 完成人物、势力与地点、榜单、体系四类对象的结构化管理。
- 提供当前作品内检索、关系双向跳转和一致性维护。
- 完成飞书《正文》与文档内现有配图的一次性迁移，并允许人工校对；素材库不纳入本版。
- 提供关键词/条件检索与摘要，不调用大模型、不生成内容。
- 提供数据导出、还原与自动快照能力，确保迁移和日常使用不丢数据（已确认，Must）。
- 在本地 Docker 环境中可用，并为未来公网部署保留空间。

### 3.3 目标优先级

1. **查找与一致性**：第一优先级，所有设计取舍以此为准。
2. **结构化覆盖**：四类核心对象必须可录入、可关联、可检索。
3. **迁移完整性**：现有设定与图片必须完整进入系统。
4. **体验与视觉**：浅绿色渐变、简洁、一目了然；但不能为了美观牺牲检索效率。

## 4. 目标用户

### 4.1 主用户

项目发起人本人：一位会同时构思多本小说、每本拥有独立世界观的个人作者。

### 4.2 用户特征

- 已有大量飞书设定资料，习惯以文档和列表组织信息。
- 能使用 Docker Desktop，接受本地部署与命令行启动。
- 愿意在迁移后做人工校对，不要求 100% 自动解析。
- 追求零成本，不接受持续付费的云服务或大模型 API。
- 对详情页的完整性与视觉整洁有明确要求。

### 4.3 非目标用户

- 普通读者（只读浏览不是第一版目标）。
- 大型创作团队（多人协作与权限不在第一版）。
- 其他公开注册作者（多租户与运营不在第一版）。

### 4.4 未来用户

未来可能开放公网只读访问，但第一版只做单用户，不实现账号、权限与多租户；协作者不是本版目标用户。

## 5. 核心使用场景

| 编号 | 场景 | 触发 | 期望流程 | 成功结果 |
|---|---|---|---|---|
| S1 | 查人物 | 写作或构思时需要确认某个角色 | 输入本名、别名或称号 → 搜索结果 → 人物详情 → 查看境界、势力、榜单、图片、大事记 → 跳转关联势力或地点 | 一次搜索即可定位，信息完整 |
| S2 | 维护一致性 | 人物改名、换势力、调整境界 | 在人物详情页修改 → 所有关联页面与榜单自动更新 | 无需手工修改多处，不产生矛盾 |
| S3 | 新建小说 | 开始构思一本新作品 | 创建作品 → 配置该作品独立的体系、榜单 → 录入人物、势力、地点 | 新作品与旧作品数据完全隔离 |
| S4 | 维护榜单 | 调整榜单席位或人物名次 | 配置榜单名称、席位数、席位顺序 → 指派人物 → 查看空缺与在榜人物 | 榜单结构清晰，可查人物在哪些榜 |
| S5 | 迁移校对 | 首次把飞书资料迁入系统 | 按固定模板整理《正文》与现有配图 → 产品内导入向导（校验/预览/确认） → 核对人物、势力、地点、榜单、体系、图片 → 人工校对 | 迁移清单无遗漏，图片不丢，层级可追溯 |
| S6 | 规则化检索 | 不想逐页翻找，想用关键词组合查询 | 输入关键词或条件（如「山海妖族 圣者境」）→ 返回匹配条目、摘要与链接 | 结果有出处，不编造，无匹配时明确提示 |
| S7 | 日常备份 | 迁移前、重大修改前或定期 | 导出全量数据 → 在空环境验证恢复 | 数据可恢复，不依赖单一环境 |

## 6. MVP 范围

### 6.1 MVP 必须交付

| ID | 能力 | 必须包含 | 验收标准 | 优先级 |
|---|---|---|---|---|
| MVP-01 | 多作品管理 | 创建、切换、编辑、删除作品（整本进回收站）；每本作品拥有独立体系与独立数据；第一版不做跨作品引用 | 两本作品可存在同名人物且互不冲突；删除/恢复可执行 | P0 |
| MVP-02 | 人物档案 | 主名称（必填）、别名、称号、境界（主境界 + 子层级）、所属势力 / 分支、1 张主图（缩略图 + 懒加载）、简介、手工大事记 | 任一别名或称号可检索；详情页字段完整；图片可上传、预览且不阻塞文字渲染 | P0 |
| MVP-03 | 势力与地点 | 势力单棵树、节点不区分类型、首领与成员；地点单棵树、类型为自由文本（带已有值建议）；人物与势力、地点的归属关系 | 势力页列出分支与成员；人物可归属；地点可关联人物与势力 | P0 |
| MVP-04 | 榜单与席位 | 自定义榜单名称、席位数 1–200（默认 100）、席位顺序、上榜人物、备注；允许空缺；同一人物同榜仅 1 席、可上多榜；不做并列（备注可写「并列」）；只可扩容，缩容仅当尾部全空 | 可创建 100 席榜单；可调整顺序；可查人物在哪些榜 | P0 |
| MVP-05 | 体系设定 | 每本作品独立一套体系；内置「境界」类别必开、名称固定、不可停用/删除；其他类别自定义（≤10 类含境界），类型普通/纪元，可新增/改名/停用/删除；每类最多两级；人物每类 0..1；势力不引用体系 | 可新增「圣体」等类别；改名后引用处同步；不同作品互不影响 | P0 |
| MVP-06 | 当前作品检索 | 一个检索入口，覆盖当前作品内人物、势力、地点、榜单、体系节点；空格分词 AND；匹配名称/别名/称号/简介及关联实体名称 | 样例集中所有实体均可被找到；结果分组并可直接跳转 | P0 |
| MVP-07 | 关系双向跳转 | 人物、势力、地点、榜单、体系详情页展示入向与出向关系 | 所有关联链接可达；无死链 | P0 |
| MVP-08 | 一致性维护 | 关系以引用而非复制；改名、换势力、改境界一处修改，所有关联处同步（限当前作品） | 至少验证改名、换势力、改境界三类操作 | P0 |
| MVP-09 | 检索结果与摘要 | 关键词或条件组合查询；返回匹配条目、摘要与链接；无匹配时明确提示；不调用大模型、不生成内容 | 预设查询集全部返回正确条目；不生成不存在的内容 | P0 |
| MVP-10 | 飞书迁移 | 仅《正文》与文档内现有配图；产品内导入向导；固定 Markdown 模板 + 图片 zip；校验/预览/原子导入；可校对实体（人物/势力/地点/榜单/体系节点）标记待校对 | 迁移清单无遗漏；图片数量一致；层级可追溯；校对记录留存 | P0 |
| MVP-11 | 数据导出与恢复 | 产品内全量导出 zip（可选含回收站，默认含）；CLI 还原；恢复/导入/删除作品/清空回收站前自动快照，保留最近 3 份 | 导出后可恢复到空环境；迁移前备份成功 | P0 |
| MVP-12 | 本地部署与单用户 | Docker Desktop 启动；容器内监听 0.0.0.0，宿主发布端口仅绑定 127.0.0.1；本地数据持久化；本版不做公网访问，未来公网必须增加访问控制 | 按文档启动可用；重启后数据不丢 | P0 |
| MVP-13 | 界面与视觉 | 浅绿色渐变、简洁；中文；桌面浏览器；页面覆盖检索、人物、势力、地点、榜单、体系、导入、回收站、设置/备份 | 用户验收通过；信息一目了然；不做移动端专门适配 | P0 |
| MVP-14 | 数据完整性校验 | 必填字段校验；同一作品同一类型主名称唯一；体系类别名称唯一；体系节点同父唯一；英文不区分大小写；禁止悬空引用；删除被引用实体前必须解除引用 | 无法保存缺失主名称的人物；删除被引用实体时阻止并提示 | P0 |
| MVP-15 | 回收站与撤销 | 作品、人物、势力、地点、榜单、体系类别、体系节点、大事记软删除；toast 撤销；逐条恢复/永久删除/清空；恢复冲突时阻止并提示；永久删除/清空前自动快照 | 删除后检索不到；撤销/恢复可用；无死链 | P0 |

### 6.2 MVP 可配置边界（已确认）

- **榜单**：只配置名称、席位数 1–200（默认 100）、席位顺序、上榜人物、备注；允许空缺与一人多榜；不做并列（备注可写「并列」）；只可扩容，缩容仅当尾部全空；**不做自动排名规则引擎**。
- **体系**：每本作品独立一套体系；内置「境界」类别必开、名称固定、不可停用/删除；其他类别自定义（≤10 类含境界），类型普通/纪元，可新增/改名/停用/删除；每类最多两级；人物每类 0..1；势力不引用体系；第一版不做跨作品共享、模板复制或全局体系库。
- **时间线**：人物与势力详情页支持手工大事记；不建立全局事件库，不做自动时间线推导。
- **图片**：人物 1 张主图；势力、地点不做图；缩略图与懒加载为 Must，上传进度与可选压缩为 Should。

### 6.3 MVP 验收前提

- 飞书《正文》与文档内现有配图可访问；素材库不纳入本版。
- 用户提供一组真实人物与势力作为检索、一致性、迁移的验收样例。
- 榜单边界、体系类别模型、备份 / 导出已确认；数据规模按 `requirements.md` 6.7 基线执行。
- 技术栈、数据模型与部署方案在架构阶段确认后才能编码。

## 7. 非目标范围

| 项目 | 不做原因 | 未来触发条件 |
|---|---|---|
| 小说正文、章节、大纲、发布 | 产品定位是设定资料库，不是写作工具 | 写作与设定引用成为高频刚需 |
| 关系图谱 | 第一版优先解决查找与一致性，图谱不是主矛盾 | 数据密度足够，且图谱能解决实际查找问题 |
| 多人协作、账号、权限 | 单用户起步，避免复杂度；协作者不是本版目标用户 | 未来开放公网只读访问时另行设计访问控制 |
| 移动端 App 或专门适配 | 桌面浏览器优先，第一版不做响应式专项 | 真实移动使用场景出现 |
| AI 生成、续写、设定创作 | 零成本优先，生成质量与审核流程不可控 | 有预算且建立人工审核流程 |
| 云端大模型 API | 与零成本约束冲突；关键词/条件检索已能满足需求 | 明确需要自然语言推理，且接受按量费用 |
| 自动排名、战力计算 | 已确认榜单只做手工席位，不做自动排名 | 未来出现明确的自动化排名规则 |
| 变更历史、审计、任意时点回滚 | 未选为第一版必须；用备份 / 快照与回收站兜底 | 多人协作或误改风险显著上升 |
| 公网运营、多租户、计费 | 第一版不是公开产品 | 决定对外开放注册 |
| 跨作品共享世界观 | 每本小说各自独立 | 出现系列作品共享人物 / 势力的需求 |
| 飞书持续双向同步 | 一次性迁移，避免同步冲突 | 飞书重新成为主要编辑入口（不建议） |
| 素材库迁移 | 用户确认本版只迁移《正文》与文档内现有配图 | 未来提供素材库清单并有明确迁移需求 |
| 通用低代码、自定义实体建模（体系类别自定义除外） | 防止「可配置」范围膨胀 | 四类对象稳定后确有新实体需求 |
| 多语言 / 国际化 | 单用户中文场景 | 出现非中文用户 |
| 复杂可视化大屏、3D 展示 | 与检索优先原则冲突 | 图谱或展示需求明确 |

## 8. 项目约束

| 类别 | 约束 |
|---|---|
| 使用形态 | 单用户；本地 Docker Desktop 运行；桌面浏览器访问；未来可部署公网 |
| 成本 | 第一版零成本优先：不采购云服务器、域名、对象存储或付费 API |
| 开发方式 | 项目发起人自己主导 + AI 辅助；无硬性截止时间；尽快可用 |
| 数据 | 本地存储；属于个人创作数据，按私密数据处理；必须可导出 / 备份 |
| 迁移 | 仅飞书《正文》与文档内现有配图一次性迁移；全量结构化 + 人工校对；素材库不纳入本版 |
| 范围 | 四类对象结构化；不做图谱、正文、协作、移动端、AI 生成、自动排名 |
| 技术 | Go + gin/gorm + Next.js + PostgreSQL 16 + Redis（仅缓存）；必须可在 Docker 中运行；不引入云端大模型；不引入持续付费依赖 |
| 未来扩展 | 可能开放公网只读访问；第一版不实现账号 / 权限，但架构阶段不得堵死扩展路径 |
| 界面 | 浅绿色渐变、简洁；中文；桌面优先；不以视觉牺牲检索效率 |
| 验收 | 项目发起人本人验收；必须用真实小说数据试用 |
| 数据规模 | 单作品 1000 人物、200 势力节点、200 地点、5 榜单 ×100 席、10 类体系类别、150 体系节点、500 张图片、作品 ≤10 |
| 性能 | 检索 P95 ≤150ms、列表 ≤500ms、保存 ≤300ms、导入 ≤90s、图片上传 ≤1s、首屏可交互 ≤2s（硬验收） |

## 12. 风险与敏感操作

- 是否涉及个人 / 敏感数据：是。小说设定与人物图片属于个人创作数据，按私密数据处理。
- 是否涉及支付：否。
- 是否涉及权限 / 多租户：第一版否；未来公网部署必须增加访问控制。
- 是否涉及生产数据库：第一版否，使用本地数据。
- 是否涉及第三方 API 密钥：第一版否；明确禁止云端大模型 API。
- 备份与回滚方式：全量导出 / 导入；迁移前快照；恢复演练。第一版不做审计与回滚功能，因此备份是唯一恢复手段。

### 12.1 关键风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 「榜单可配置」范围膨胀 | 第一版失控，变成低代码平台 | 只做已确认的最小配置；新增配置项必须人工批准 |
| 检索预期落差 | 用户期待自然语言理解，实际只是关键词 / 条件检索 | 明确标注为「检索」；用预设查询集验收；不承诺推理能力 |
| 迁移保真度不足 | 人物、势力、图片或层级丢失 | 按固定模板整理《正文》与现有配图；迁移清单、数量核对、人工校对、用户签收 |
| 无审计 / 任意时点回滚 | 误改或误删后无法追溯 | 导出 / 备份 / 自动快照 + 回收站作为可靠性底线；重大修改前快照 |
| 「美观」主观 | 验收反复，范围蔓延 | 先定浅绿色渐变与简洁方向；以真实页面评审，不追求装饰复杂度 |
| 多作品独立体系 | 数据模型复杂，页面易混用 | 每本作品独立数据域；第一版禁止跨作品引用 |
| 模板整理与解析成本 | 飞书排版不完全符合固定模板，人工整理耗时 | 提供模板、示例、校验预览与待校对清单；不承诺兼容任意飞书原始排版 |
| 零成本与未来公网部署 | 公网托管可能产生费用 | 零成本只约束第一版本地使用；公网费用另行确认 |
| 单用户与未来多用户 | 过早建设权限，或后续难以扩展 | 第一版不建权限；架构阶段只保留必要扩展点 |
