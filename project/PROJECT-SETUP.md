## 2. 项目概述

### 2.1 背景

写小说时，人物、人物图片、境界、称号、所属势力、地点、势力成员、排行榜等信息分散在飞书文档中，依靠标题层级、括号备注和列表混合表达。随着设定增多，会出现三个问题：

1. 查找成本高：想确认一个角色的势力、境界或榜单名次，需要在多个章节和列表之间翻找。
2. 同一实体多名称：一个人物可能同时拥有本名、化名、称号和境界描述，例如「司空摘天（神逆）（山海帝君）（帝境五重天）」，没有统一的主名称与检索入口。
3. 修改容易不一致：改名、换势力、调整境界后，需要人工同步多处，容易产生矛盾设定。

### 2.2 核心问题

本项目要解决的不是「如何写小说」，而是：

- 如何把散落的设定变成**可检索、可关联、可维护**的结构化资料。
- 如何保证同一实体只有一份权威数据，修改后所有关联位置自动同步。
- 如何让多本小说各自拥有独立世界观，又不互相污染。

### 2.3 产品定位

**小说设定的结构化资料库 + 检索与一致性维护工具。**

它不是：

- 小说正文写作工具；
- 关系图谱或可视化大屏工具；
- 多人协作平台；
- AI 内容生成工具。

### 2.4 输入事实（来自飞书《正文》）

- 文档性质：世界观设定集，不是小说正文。
- 已包含六类内容：纪元史、星空地理、星曜 / 星命 / 十五境体系、三张榜单、万族传（种族 / 势力 / 分支 / 首领）、人物与配图。
- 三张榜单：封神榜、草黄纸、星火榜，均为 1-100 的固定席位，目前基本为空。
- 人物是多值实体：可同时拥有本名、化名、称号、境界（含重天等子层级），并归属某个势力或分支。
- 势力存在层级：万族 → 族 → 分支（如山海妖族 → 山海七神天 → 心神天 / 水神天 / …），分支下有首领与成员。
- 文档中已有真实人物配图，说明「人物图片」是实际需求，不是设想。
- 当前信息依靠「标题层级 + 括号备注 + 列表」混合表达，没有统一字段，这正是检索困难与不一致的根源。

## 3. 项目目标

### 3.1 长期目标

- 成为作者本人管理小说设定的**唯一可信数据源**，替代飞书文档的日常查阅。
- 支持多本小说，每本拥有独立世界观、独立体系与独立数据。
- 为后续写作、设定扩展和系列作品复用提供可靠基础。

### 3.2 第一版目标

- 完成人物、势力与地点、榜单、体系四类对象的结构化管理。
- 提供全局检索、关系双向跳转和一致性维护。
- 完成飞书《正文》与素材库的一次性迁移，并允许人工校对。
- 提供规则化检索问答，不调用大模型。
- 提供数据导出与备份能力，确保迁移和日常使用不丢数据（建议，待确认）。
- 在本地 Docker 环境中可用，并为未来公网部署保留空间。

### 3.3 目标优先级

1. **查找与一致性**：第一优先级，所有设计取舍以此为准。
2. **结构化覆盖**：四类核心对象必须可录入、可关联、可检索。
3. **迁移完整性**：现有设定与图片必须完整进入系统。
4. **体验与视觉**：浅绿色渐变、简洁、一目了然；但不能为了美观牺牲检索效率。

## 4. 目标用户

### 4.1 主用户

项目发起人本人：一位会同时构思多本小说、每本拥有独立世界观的个人作者。

### 4.2 用户特征

- 已有大量飞书设定资料，习惯以文档和列表组织信息。
- 能使用 Docker Desktop，接受本地部署与命令行启动。
- 愿意在迁移后做人工校对，不要求 100% 自动解析。
- 追求零成本，不接受持续付费的云服务或大模型 API。
- 对详情页的完整性与视觉整洁有明确要求。

### 4.3 非目标用户

- 普通读者（只读浏览不是第一版目标）。
- 大型创作团队（多人协作与权限不在第一版）。
- 其他公开注册作者（多租户与运营不在第一版）。

### 4.4 未来用户

未来可能扩展少量协作者或开放给其他作者，但第一版只做单用户，不实现账号、权限与多租户。

## 5. 核心使用场景

| 编号 | 场景 | 触发 | 期望流程 | 成功结果 |
|---|---|---|---|---|
| S1 | 查人物 | 写作或构思时需要确认某个角色 | 输入本名、别名或称号 → 搜索结果 → 人物详情 → 查看境界、势力、榜单、图片、大事记 → 跳转关联势力或地点 | 一次搜索即可定位，信息完整 |
| S2 | 维护一致性 | 人物改名、换势力、调整境界 | 在人物详情页修改 → 所有关联页面与榜单自动更新 | 无需手工修改多处，不产生矛盾 |
| S3 | 新建小说 | 开始构思一本新作品 | 创建作品 → 配置该作品独立的体系、榜单 → 录入人物、势力、地点 | 新作品与旧作品数据完全隔离 |
| S4 | 维护榜单 | 调整榜单席位或人物名次 | 配置榜单名称、席位数、席位顺序 → 指派人物 → 查看空缺与在榜人物 | 榜单结构清晰，可查人物在哪些榜 |
| S5 | 迁移校对 | 首次把飞书资料迁入系统 | 导入《正文》与素材库 → 核对人物、势力、地点、榜单、体系、图片 → 人工修正 | 迁移清单无遗漏，图片不丢，层级可追溯 |
| S6 | 规则化问答 | 不想逐页翻找，想用关键词组合查询 | 输入关键词或条件（如「山海妖族 圣者境」）→ 返回匹配条目、摘要与链接 | 答案有出处，不编造，无匹配时明确提示 |
| S7 | 日常备份 | 迁移前、重大修改前或定期 | 导出全量数据 → 在空环境验证恢复 | 数据可恢复，不依赖单一环境 |

## 6. MVP 范围

### 6.1 MVP 必须交付

| ID | 能力 | 必须包含 | 验收标准 | 优先级 |
|---|---|---|---|---|
| MVP-01 | 多作品管理 | 创建、切换、编辑作品；每本作品拥有独立体系与独立数据；第一版不做跨作品引用 | 两本作品可存在同名人物且互不冲突 | P0 |
| MVP-02 | 人物档案 | 主名称（用户指定）、别名、称号、境界（主境界 + 子层级）、所属势力 / 分支、人物图片、简介、手工大事记 | 任一别名或称号可检索；详情页字段完整；图片可上传与预览 | P0 |
| MVP-03 | 势力与地点 | 种族 / 势力层级、分支、首领、成员；星域、星城、秘境等地点；人物与势力、地点的归属关系 | 势力页列出分支与成员；人物可归属；地点可关联人物与势力 | P0 |
| MVP-04 | 榜单与席位 | 自定义榜单名称、席位数、席位顺序、上榜人物、备注；允许席位空缺；同一人物可上多榜；是否允许并列待确认 | 可创建 100 席榜单；可调整顺序；可查人物在哪些榜 | P0 |
| MVP-05 | 体系设定 | 每本作品独立定义纪元、星曜品级、星命、十五境等层级与名称（含重天等子层级）；人物与势力可引用 | 修改体系名称后引用处同步更新；不同作品互不影响 | P0 |
| MVP-06 | 全局搜索 | 一个搜索入口，覆盖人物、势力、地点、榜单、体系的名称、别名、称号与描述 | 样例集中所有实体均可被找到；结果分组并可直接跳转 | P0 |
| MVP-07 | 关系双向跳转 | 人物、势力、地点、榜单、体系详情页展示入向与出向关系 | 所有关联链接可达；无死链 | P0 |
| MVP-08 | 一致性维护 | 关系以引用而非复制；改名、换势力、改境界一处修改，全局同步 | 至少验证改名、换势力、改境界三类操作 | P0 |
| MVP-09 | 规则化检索问答 | 关键词或条件组合查询；返回匹配条目、摘要与链接；无匹配时明确提示；不调用大模型 | 预设查询集全部返回正确条目；不生成不存在的内容 | P1 |
| MVP-10 | 飞书迁移 | 《正文》与素材库一次性导入；人物、势力、地点、榜单、体系结构化；图片保留；允许人工校对 | 迁移清单无遗漏；图片数量一致；层级可追溯；校对记录留存 | P0 |
| MVP-11 | 数据导出与备份（建议，待确认） | 全量导出；可恢复；迁移前快照 | 导出后可恢复到空环境；迁移前备份成功 | P0（待确认） |
| MVP-12 | 本地部署与单用户 | Docker Desktop 启动；浏览器访问；本地数据持久化；公网部署时增加访问口令 | 按文档启动可用；重启后数据不丢 | P0 |
| MVP-13 | 界面与视觉 | 浅绿色渐变、简洁；中文；桌面浏览器；核心页面覆盖作品、人物、势力 / 地点、榜单、体系、搜索、问答 | 用户验收通过；信息一目了然；不做移动端专门适配 | P1 |
| MVP-14 | 数据完整性校验 | 必填字段校验；同一作品、同一实体类型内主名称唯一性；禁止悬空引用；删除被引用实体前必须解除引用 | 无法保存缺失主名称的人物；删除被引用实体时阻止并提示 | P0 |

### 6.2 MVP 可配置边界（建议，待确认）

- **榜单**：只配置名称、席位数、席位顺序、上榜人物、备注；允许空缺与一人多榜；是否允许并列待确认；**不做自动排名规则引擎**。
- **体系**：每本作品独立定义层级与名称；第一版不做跨作品共享、模板复制或全局体系库。
- **时间线**：人物与势力详情页支持手工大事记；不建立全局事件库，不做自动时间线推导。
- **图片**：人物图片为必须；势力、地点图片是否为第一版必须，待确认。

### 6.3 MVP 验收前提

- 素材库完成盘点，明确格式、数量与迁移边界。
- 用户提供一组真实人物与势力作为检索、一致性、迁移的验收样例。
- 用户确认榜单最小可配置边界与备份 / 导出是否进入 MVP。
- 技术栈、数据模型与部署方案在架构阶段确认后才能编码。

## 7. 非目标范围

| 项目 | 不做原因 | 未来触发条件 |
|---|---|---|
| 小说正文、章节、大纲、发布 | 产品定位是设定资料库，不是写作工具 | 写作与设定引用成为高频刚需 |
| 关系图谱 | 第一版优先解决查找与一致性，图谱不是主矛盾 | 数据密度足够，且图谱能解决实际查找问题 |
| 多人协作、账号、权限 | 单用户起步，避免复杂度 | 出现真实协作者或共享需求 |
| 移动端 App 或专门适配 | 桌面浏览器优先，第一版不做响应式专项 | 真实移动使用场景出现 |
| AI 生成、续写、设定创作 | 零成本优先，生成质量与审核流程不可控 | 有预算且建立人工审核流程 |
| 云端大模型 API | 与零成本约束冲突；规则化问答已能满足检索需求 | 明确需要自然语言推理，且接受按量费用 |
| 自动排名、战力计算 | 榜单语义尚未确定，先做可配置席位 | 榜单规则与战力体系确认 |
| 变更历史、审计、回滚 | 未选为第一版必须；用备份 / 导出兜底 | 多人协作或误改风险显著上升 |
| 公网运营、多租户、计费 | 第一版不是公开产品 | 决定对外开放注册 |
| 跨作品共享世界观 | 每本小说各自独立 | 出现系列作品共享人物 / 势力的需求 |
| 飞书持续双向同步 | 一次性迁移，避免同步冲突 | 飞书重新成为主要编辑入口（不建议） |
| 通用低代码、自定义实体建模 | 防止「可配置」范围膨胀 | 四类对象稳定后确有新实体需求 |
| 多语言 / 国际化 | 单用户中文场景 | 出现非中文用户 |
| 复杂可视化大屏、3D 展示 | 与检索优先原则冲突 | 图谱或展示需求明确 |

| 界面 | 浅绿色渐变、简洁；中文；桌面优先；不以视觉牺牲检索效率 |
| 验收 | 项目发起人本人验收；必须用真实小说数据试用 |
| 数据规模 | `TBD`，架构阶段确认 |
| 性能 | 本地搜索需满足即时检索体验；具体指标在架构阶段确定 |

## 12. 风险与敏感操作

- 是否涉及个人 / 敏感数据：是。小说设定与人物图片属于个人创作数据，按私密数据处理。
- 是否涉及支付：否。
- 是否涉及权限 / 多租户：第一版否；未来公网部署必须增加访问控制。
- 是否涉及生产数据库：第一版否，使用本地数据。
- 是否涉及第三方 API 密钥：第一版否；明确禁止云端大模型 API。
- 备份与回滚方式：全量导出 / 导入；迁移前快照；恢复演练。第一版不做审计与回滚功能，因此备份是唯一恢复手段。

### 12.1 关键风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 「榜单可配置」范围膨胀 | 第一版失控，变成低代码平台 | 只做已确认的最小配置；新增配置项必须人工批准 |
| 规则化问答预期落差 | 用户期待自然语言理解，实际只是关键词 / 条件检索 | 明确标注为「检索问答」；用预设查询集验收；不承诺推理能力 |
| 迁移保真度不足 | 人物、势力、图片或层级丢失 | 先盘点素材库；迁移清单、数量核对、人工校对、用户签收 |
| 无审计 / 回滚 | 误改或误删后无法追溯 | 导出 / 备份作为可靠性底线；重大修改前快照 |
| 「美观」主观 | 验收反复，范围蔓延 | 先定浅绿色渐变与简洁方向；以真实页面评审，不追求装饰复杂度 |
| 多作品独立体系 | 数据模型复杂，页面易混用 | 每本作品独立数据域；第一版禁止跨作品引用 |
| 素材库格式未知 | 迁移方案无法定稿 | 在架构阶段前完成素材库盘点 |
| 零成本与未来公网部署 | 公网托管可能产生费用 | 零成本只约束第一版本地使用；公网费用另行确认 |
| 单用户与未来多用户 | 过早建设权限，或后续难以扩展 | 第一版不建权限；架构阶段只保留必要扩展点 |
