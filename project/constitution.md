# Project Constitution

本文件是项目长期有效的工程原则。修改本文件必须经过人工确认。

## 1. 产品原则
- 所有功能必须对应已确认的用户需求或明确批准的技术任务。
- 不擅自扩大 MVP 范围。
- 未确认的信息标记 TBD，不得伪装成事实。

## 2. 架构原则
- 优先复用现有能力和成熟依赖。
- 采用满足当前需求的最简单架构。
- 模块职责、依赖方向和数据边界必须清楚。
- 重大技术决策记录 ADR。

## 3. 编码原则
- 遵循仓库已有风格和技术栈惯例。
- 不进行无关重构。
- 不吞掉异常，不返回伪成功。
- 不硬编码密钥、凭证和环境差异配置。

## 4. 测试原则
- 新增行为必须有相应测试。
- Bug 修复优先增加能复现问题的回归测试。
- 未实际执行的测试不得标记 PASS。
- 高风险变更必须有集成或 E2E 验证。

## 5. 安全原则
- 默认最小权限。
- 服务端必须校验身份、权限和输入。
- 不在日志中输出密钥、令牌和敏感数据。
- 破坏性数据操作、生产操作必须人工批准。

## 6. 变更原则
- 每个变更必须有目标、范围、非目标、DoD。
- 超出任务范围先暂停并请求批准。
- 代码、Spec、API 和架构文档保持一致。
- 变更完成后更新长期规格并归档。

## 7. 交付原则
- PR/MR 必须提供测试结果和风险说明。
- 发布后执行 Smoke Test。
- 必须有可执行的回滚或恢复方案。
