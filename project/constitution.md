# Project Constitution

> 本文件是项目长期有效的产品与工程原则。修改必须经项目发起人明确确认。
> 与 `project/requirements.md` v1.0 冲突时，以 `requirements.md` 为准；与 `PROJECT-SETUP.md` 冲突时，以经确认的 PROJECT-SETUP 为准；未确认内容标记 `TBD`，不得当作事实。
> 本文件不规定具体技术栈；技术选型在架构阶段确认，并记录到 `project/adr/`。

## 0. 项目第一原则

1. **检索优先**：任何设计取舍，先问「是否让用户更快查到想要的设定」。
2. **一致性优先**：同一实体只有一份权威数据；关系用引用，不用复制文本；改一处，全局同步。
3. **单一可信数据源**：系统是设定的唯一事实来源；飞书文档迁移完成后归档，不再作为日常查阅入口。
4. **每本小说独立**：作品是数据边界；每本小说拥有独立世界观、独立体系与独立数据；第一版不做跨作品引用。
5. **本地优先、零成本**：第一版本地 Docker 运行，不引入付费云服务、付费 API 或云端大模型；未来公网部署另行确认费用与访问控制。
6. **范围克制**：MVP 之外不「顺手做」；新增范围必须有明确需求、成功标准与人工批准。

## 1. 产品原则

- 所有功能必须对应已确认的用户需求或明确批准的技术任务。
- 不擅自扩大 MVP 范围；非目标列表是硬边界，不是建议。
- 四类核心对象必须结构化：人物、势力与地点、榜单、体系。
- 境界必须支持主境界与子层级（如帝境五重天、圣者境八重天），不得整体存为自由文本。
- 体系类别按作品自定义（≤10 类，含内置「境界」）；「境界」必开、名称固定、不可停用/删除；星曜、星命、圣体等类别必须由数据配置驱动，不得在代码中写死。
- 第一版优先保证「查得到」与「改一处全局同步」，再考虑体验与视觉打磨。
- 详情页必须满足：核心资料完整、关系双向可跳转、人物与势力有手工大事记、无死链。
- 榜单只做最小可配置：席位 1–200（默认 100）、允许空缺、一人同榜一席、不做并列；不做自动排名规则、战力计算或数值平衡。
- 规则化检索问答只做检索与摘要，不生成内容；答案必须引用系统内条目；无匹配时明确提示，不得编造。
- 第一版明确不做：关系图谱、小说正文与章节、多人协作与权限、移动端专门适配、AI 生成与续写、公网多租户与运营。
- 未确认的信息标记 `TBD`；建议性内容必须标注「建议，待确认」，不得伪装成已确认事实。

## 2. 数据原则

- 每个实体必须属于且仅属于一本作品；第一版禁止跨作品引用。
- 主名称是实体的权威标识，由用户显式指定，不允许系统猜测；别名与称号是一等检索入口，不得只存放在备注或简介里。
- 关系必须通过引用表达，不得复制文本；改名、换势力、改境界只允许改一处。
- 禁止悬空引用；删除被引用实体前必须解除引用；同一作品、同一实体类型内主名称必须唯一；体系类别名称同作品唯一；英文名称唯一性校验不区分大小写。
- 必填字段必须校验；不允许保存没有主名称的人物、势力、地点或榜单。
- 人物图片与实体绑定；迁移必须保留图片；图片不丢失是验收项。
- 手工大事记只保存文本与可选时间标签；第一版不建立全局事件库，不做自动时间线推导。
- 数据必须可导出、可恢复；全量导出、CLI 还原与自动快照是 MVP 必须（Must）；恢复、导入、删除作品、清空回收站前必须快照，保留最近 3 份。
- 第一版不做变更历史与审计；恢复手段为备份 / 快照与回收站，不做任意时点回滚，因此不得用「以后再补」的态度对待备份与回收站。
- 个人创作数据按私密数据处理；未经项目发起人批准，不得上传到任何外部服务。
- 飞书只做一次性迁移；迁移范围仅《正文》与文档内现有配图，素材库不纳入本版；迁移完成后归档；第一版不做运行时依赖或双向同步。

## 3. 架构原则

- 采用满足当前需求的最简单架构；不为猜测的未来需求过度设计。
- 必须能在本地 Docker Desktop 中运行，并通过桌面浏览器访问。
- 架构不得堵死未来公网部署，但第一版不实现多用户、权限或多租户。
- 零成本优先：不引入持续付费的云服务、API、对象存储或大模型服务；优先使用成熟依赖。
- 技术栈在架构阶段确认；确认前不得开始编码，不得用代码倒逼产品决策。
- 单用户是第一版前提；不建设账号与权限体系；公网部署时必须增加访问控制。
- 数据必须本地持久化；重启不丢数据；迁移与备份方案必须在架构阶段明确。
- 模块职责、依赖方向与数据边界必须清楚；重大技术决策记录 ADR。
- 不得把「单用户」硬编码到无法扩展的程度；但也不得提前建设多用户能力。

## 4. 编码原则

- 遵循仓库已有风格与技术栈惯例；不进行无关重构。
- 不吞掉异常，不返回伪成功，不用假数据填充真实页面。
- 不硬编码密钥、凭证、环境差异配置，也不硬编码某本小说、某个体系或某张榜单。
- 作品、体系、榜单必须由数据配置驱动；新增小说不得修改代码。
- 检索必须在当前作品内覆盖名称、别名、称号、简介与关联实体名称；新增实体类型必须接入检索，否则不算完成。
- 详情页关系必须双向可跳转；新增关系必须同时定义反向展示。
- 改名、换势力、改境界、删除必须走统一的完整性校验，不得绕过。
- 中文界面文案；交付不得留下占位文本、调试入口或未完成按钮。
- 未经批准不得新增依赖、修改基础设施或改动公共数据契约。

## 5. 测试原则

- 新增行为必须有相应测试；没有测试的行为不算完成。
- Bug 修复优先增加能复现问题的回归测试。
- 搜索、一致性、关系跳转、迁移、备份恢复必须有明确验收测试。
- 一致性测试至少覆盖：改名、换势力、改境界三类操作。
- 迁移测试至少覆盖：实体数量、图片数量、层级关系、无死链、人工校对记录。
- 规则化问答测试使用预设查询集；答案必须有出处；无匹配必须明确提示。
- 未实际执行的测试不得标记 `PASS`；未运行标记 `NOT RUN`；阻塞标记 `BLOCKED`。
- 高风险变更必须有集成或 E2E 验证。
- 使用真实设定数据测试时，不得把完整私密内容写入日志或提交到仓库。

## 6. UX 与界面原则

- 视觉方向为浅绿色渐变、简洁；信息优先，不以装饰牺牲检索效率。
- 中文界面；桌面浏览器优先；第一版不做移动端专门适配。
- 提供一个当前作品内的检索入口；结果按实体类型分组；名称、别名、称号、简介与关联实体名称必须可命中。
- 详情页首屏展示核心资料；关系、时间线、图片必须清晰可见。
- 所有关联链接必须可达；不允许死链；空状态必须说明下一步操作。
- 禁止用复杂图表、装饰性动画或大段视觉特效干扰查找。
- 术语必须与小说设定一致（境界、势力、榜单、体系等）；术语表在后续 `glossary.md` 维护。
- 「美观」由项目发起人本人验收；验收标准是清晰、整洁、一目了然，而不是视觉复杂度。

## 7. 安全与隐私原则

- 小说设定与人物图片属于个人创作数据，默认私有，默认本地存储。
- 公网部署必须有访问控制；第一版不开放注册，不做多租户。
- 本地服务默认只绑定本机，不对公网裸露；公网暴露必须经过人工批准。
- 不在日志、仓库或错误信息中输出密钥、令牌或完整私密设定。
- 第一版不使用第三方 API 密钥；明确禁止云端大模型 API。
- 破坏性操作（删除、批量修改、迁移覆盖）必须人工确认，并在操作前备份。
- 生产环境或公网部署必须人工批准，并具备恢复方案。

## 8. 变更与范围原则

- 每个变更必须有目标、范围、非目标与 DoD。
- 超出任务范围时先暂停并请求批准，不得默默扩展。
- 代码、Spec、API 与架构文档必须保持一致。
- MVP 非目标是硬边界；新增一项必须说明原因、用户价值、成功标准，并获得明确批准。
- 修改本宪法必须获得项目发起人的明确批准。
- 不做「顺手」优化、无关重构或未被要求的功能。
- 范围变更必须记录在 `PROJECT-SETUP.md` 或对应 `changes/` 文档中。

## 9. 交付与验收原则

- DoD 必须满足：验收标准达成、必要检查通过、文档同步、用户评审通过。
- 迁移验收必须包含：迁移清单、数量核对、图片核对、层级抽查、人工校对记录与用户签收。
- 迁移前、公网部署前必须完成可恢复备份；必须执行一次恢复演练。
- 发布后必须执行 Smoke Test。
- 第一版没有审计功能，也没有任意时点回滚；必须有明确的备份、快照、回收站与恢复方案。
- 不得声称执行过未执行的命令、测试或部署；不得伪造日志、截图、指标或链接。
- 交付说明必须包含可复现的启动、迁移、备份与恢复步骤。

## 10. 决策与记录原则

- 所有结论必须区分：已确认、待确认、建议。
- 技术架构决策必须记录 ADR；产品范围决策记录在 `PROJECT-SETUP.md`。
- 文档之间发生冲突时，停止并报告，不得静默选择其中一个。
- 项目发起人是产品范围、架构、数据模型、迁移方案与部署的最终批准人。
- `TBD` 必须显式保留；Agent 不得自行编造缺失信息。

## 11. 不可协商的第一版边界

| 边界 | 内容 |
|---|---|
| 使用形态 | 单用户；本地 Docker；桌面浏览器；未来公网部署必须增加访问控制 |
| 数据边界 | 每本小说独立世界观；第一版不做跨作品引用 |
| 核心对象 | 人物、势力与地点、榜单、体系 |
| 检索要求 | 当前作品内检索覆盖名称、别名、称号、简介与关联实体名称；详情页关系双向可跳转；人物与势力有手工大事记 |
| 一致性 | 引用而非复制；改一处全局同步；禁止悬空引用 |
| 榜单 | 席位 1–200（默认 100）、允许空缺、一人同榜一席、不做并列；不做自动排名规则与战力计算 |
| AI | 只做规则化检索问答；不调用大模型；不生成内容 |
| 迁移 | 仅飞书《正文》与文档内现有配图一次性迁移；素材库不纳入本版；全量结构化 + 人工校对；不做持续同步 |
| 明确不做 | 小说正文与章节、关系图谱、多人协作与权限、移动端专门适配、AI 生成与续写、公网多租户、跨作品共享世界观 |
| 视觉 | 浅绿色渐变、简洁、中文、桌面优先 |
| 成本 | 第一版零成本优先；不引入付费 API、云服务或云端大模型 |
| 可靠性 | 全量导出、CLI 还原、自动快照（保留 3 份）为 MVP 必须；迁移与公网部署前必须有可恢复备份 |

## 12. 原则冲突时的优先级

当原则发生冲突时，按以下顺序取舍：

1. 数据不丢失与隐私安全。
2. 数据一致性与正确性。
3. 检索效率与可查找性。
4. 范围克制与零成本。
5. 视觉与体验。
6. 开发便利。

例如：为了「好看」而增加复杂图谱，违反第 3、4 条；为了「可配置」而引入通用低代码，违反第 4 条；为了开发方便而复制实体文本，违反第 2 条。
