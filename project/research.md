## 2. 用户与替代方案

- 【事实】目标用户是项目发起人本人：会同时构思多本小说、每本拥有独立世界观的个人作者；已有大量飞书设定资料，能使用 Docker Desktop，追求零成本。
- 【事实】当前资料以「标题层级 + 括号备注 + 列表」混合表达，同一人物可能同时拥有本名、化名、称号与境界描述，没有统一主名称与检索入口。
- 【判断】现有替代方案主要有三类：飞书文档 / Notion / Obsidian 等通用知识库；Kanka、World Anvil、LegendKeeper、Campfire 等世界构建工具；自建表格或脚本。
- 【判断】通用知识库缺少「别名一等检索 + 引用一致性 + 榜单席位 + 每作品独立体系」的组合能力；世界构建工具多为英文优先、SaaS、付费订阅，且不针对中文网文的境界层级与榜单席位建模。
- 【判断】本项目成立的前提不是「再做一个 wiki」，而是：通用工具无法同时满足上述五项组合需求，且用户接受本地部署与固定模板迁移成本。

### 3.2 竞品结论

- 【判断】市场存在大量「世界构建」工具，但共同假设是「英文 / SaaS / 通用实体」，未针对「中文网文的多名称人物 + 境界层级 + 可配置席位榜单」建模。
- 【判断】本项目有差异化空间，但这是小众需求；因此更不能扩张范围，否则会向通用世界构建工具演化，直接对上成熟竞品。
- 【判断】最值得借鉴的三点：Kanka 的作品作用域、LegendKeeper 的 wiki 检索与导出体验、World Anvil 的体系化设定信息组织。

## 5. 市场判断

- 【判断】目标市场是「个人作者 / 世界观创作者」的小众工具市场，不是大众写作平台。
- 【判断】用户对「检索快、改一处同步、迁移不丢图」的敏感度远高于「功能多、视觉炫」。
- 【判断】零成本与本地私密是差异化优势，不是妥协；云服务、协作、AI 生成会直接破坏这两个优势。
- 【待验证】用户是否愿意为迁移整理固定模板；若整理成本过高，迁移范围需重新评估。

## 6. 技术、成本、合规与运营风险

| 编号 | 风险 | 等级 | 触发条件 | 影响 | 缓解方向 | 状态 |
|---|---|---|---|---|---|---|
| R-01 | 中文检索召回不足 | 高 | 默认 tokenizer 或短关键词查询 | 别名、称号查不到，直接违背检索优先原则 | 先做真实样例基准；必要时 `trigram` / `pg_trgm` / 外部引擎 | 【待验证】 |
| R-02 | 迁移保真度不足 | 高 | 飞书排版不完全符合固定模板、图片 zip 缺失 | 人物、层级、图片丢失，迁移验收失败 | 固定模板 + 校验预览 + 数量核对 + 人工校对 + 签收 | 【待验证】 |
| R-03 | 备份 / 导出风险 | 高 | 误删、清空回收站、覆盖恢复 | 无审计、无任意时点回滚，数据永久丢失 | 全量导出、CLI 还原、自动快照保留 3 份、恢复演练 | 已关闭（Must） |
| R-04 | 范围膨胀 | 中高 | 「榜单可配置」「详情页功能齐全」被不断扩展 | 演化为低代码平台，进度失控 | 最小配置边界；新增项须人工批准 | 持续监控 |
| R-05 | SQLite 单写者限制 | 已消除 | 未来公网多用户并发写 | 写锁排队，体验下降 | **P4 已决策采用 PostgreSQL 16（ADR-002），该风险不再适用** | 【事实】+【判断】 |
| R-06 | 外键建模/删除顺序错误导致悬空引用 | 中 | 多态引用、跨作品引用、物理删除顺序 | 删除后留下死链 | PostgreSQL FK + `ON DELETE RESTRICT` + 服务层引用校验 + 完整性测试 | 【事实】 |
| R-07 | Docker volume 误删 | 中 | 用户执行 `docker compose down -v` | 数据永久丢失 | 文档显著警告；操作前备份；提供导出入口 | 【事实】 |
| R-08 | 检索预期落差 | 中 | 用户期待自然语言推理 | 满意度下降，被认为「不好用」 | 明确「检索 + 摘要 + 出处」定位；预设查询集验收 | 【判断】 |
| R-09 | 许可证风险 | 中 | 复制 Kanka / Wiki.js / AppFlowy 代码 | 开源义务或商业限制 | 只借鉴模式；建立许可证白名单 | 【事实】+【判断】 |
| R-10 | Windows Docker Desktop 文件性能 | 中低 | 数据卷跨文件系统挂载、大量小图片 | 迁移或图片加载变慢 | 使用命名 volume；避免绑定宿主机目录做数据库存储 | 【待验证】 |
| R-11 | 未来公网安全 | 中 | 直接暴露端口 | 私密创作数据泄露 | 第一版只绑本机；公网必须加访问控制 | 已识别 |
| R-12 | 数据规模超基线 | 中 | 实际数据大于基线 | 分页、索引、检索性能判断失真 | 按 1000 人物 / 200 势力 / 200 地点 / 5 榜 ×100 席 / 10 类体系 / 150 节点 / 500 图 / 作品 ≤10 基线设计 | 已确认基线 |
| R-13 | 成本风险：未来公网托管、域名、对象存储产生持续费用 | 中 | 决定开放公网访问 | 破坏「零成本」前提，或被迫长期自费维护 | 第一版只做本机零成本；公网费用与方案另行确认 | 已识别 |
| R-14 | 运营/维护风险：单人维护、模板与迁移支持成本 | 中低 | 长期使用后模板变更、数据增长、依赖升级 | 维护负担上升，工具不可持续 | 固定模板版本化、导出/恢复可用、尽量少依赖、文档化操作 | 已识别 |

## 9. 对产品方向的启示

1. 产品定位应保持「结构化资料库 + 检索与一致性工具」，不扩展到写作、图谱、协作或 AI 生成。
2. 检索是第一优先级；技术选型必须先通过中文检索基准，不能被框架反向绑定。
3. 迁移必须按「固定模板 + 产品内向导 + 人工校对 + 用户签收」设计，不承诺全自动解析任意飞书排版。
4. 备份 / 导出 / 快照是数据可靠性的底线，必须进入 MVP（Must），不能后补。
5. 体系类别必须由数据配置驱动；星曜、星命、圣体等名称不得写死。
6. 范围越小越安全；每新增一项配置能力，都必须有明确需求与人工批准。
